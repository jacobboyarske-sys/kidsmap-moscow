# Туториал 5. Семантический поиск по событиям (embeddings)

(~3-4 часа)

Категории у всех трёх текущих источников уже приходят готовыми (у kudago.com — из
API, у playforsoul.ru/mozart-for-kids.ru — через написанные вручную правила
маппинга), так что классификатор категорий сейчас решал бы несуществующую
проблему. Вместо этого — то, что реально полезно пользователю приложения:
**поле поиска по смыслу**. Пишете "что-то спокойное для трёхлетки в дождливый
день" — получаете релевантные события, даже если в тексте события нет ни одного
дословного совпадения с запросом.

Как и раньше: код пишете вы сами вместе с Claude Code — ниже объяснение концепций и
формулировки задач, а не готовые файлы для копирования.

## Шаг 1. Почему embeddings, а не TF-IDF

TF-IDF сравнивает тексты по *словам*: он найдёт документ, где встречается слово
"весело", только если в запросе тоже есть слово "весело". **Embeddings** (векторные
представления текста от предобученной нейросети) кодируют *смысл* — вектор для
"весело" и вектор для "радостно" окажутся близко друг к другу в пространстве
признаков, хотя слова разные. Это и есть разница между поиском по ключевым
словам и поиском по смыслу.

Возраст по-прежнему остаётся на regex-правилах, а не на ML/embeddings — он
буквально написан в тексте ("6+", "12+"), гадать по смыслу тут нечего.

**Важная оговорка по стеку:** библиотека `sentence-transformers` тянет за собой
**PyTorch** — тяжёлая зависимость (сотни МБ, заметно дольше `pip install`, чем всё,
что было в проекте до сих пор). Осознанный компромисс ради смыслового поиска.

## Шаг 3. Установить sentence-transformers и выбрать модель

```powershell
pip install sentence-transformers
```

Модель — **`cointegrated/rubert-tiny2`**: маленькая (~50 МБ), заточена под русский
язык, быстро считает эмбеддинги. Для коротких описаний событий этого достаточно —
крупная мультиязычная модель (сотни МБ) точнее на сложных/смешанных текстах, но
здесь это не тот случай.

Модель скачается автоматически при первом использовании (кэшируется в
`~/.cache/huggingface/hub/`, не внутри проекта — повторно скачивать не придётся,
но и в `.gitignore` проекта добавлять эту папку не нужно, она вне его).

**Проверка на актуальность (не полагайтесь тут на память Claude Code — знания
модели имеют дату среза и могут отставать):** на момент этого туториала более
современный вариант — `Qwen3-Embedding-0.6B` (лучше качество, но ~12x больше
параметров и заметно медленнее на CPU без GPU). Для маленького pet-проекта с
короткими описаниями событий и без GPU разница в качестве не стоит потери в
скорости — `rubert-tiny2` сознательно выбран ради лёгкости и скорости на
обычном ноутбуке, а не потому что это единственный вариант.

## Шаг 4. src/embed_events.py — предвычислить векторы

Офлайн-скрипт по аналогии с `train_classifier.py`: не считаем эмбеддинги на каждый
поисковый запрос заново (медленно), а считаем один раз для всех событий и сохраняем
на диск.

1. Загрузить события через `load_events()` (сейчас — `data/events.json`).
2. Для каждого события собрать текст (`f"{title}. {description}"`).
3. `SentenceTransformer("cointegrated/rubert-tiny2").encode(texts)` — вернёт
   массив векторов (`numpy.ndarray`, размер `[N, 312]`).
4. Сохранить два файла:
   - `data/event_embeddings.npy` — сами векторы (`np.save`);
   - `data/event_embeddings_keys.json` — список ключей событий в том же порядке
     (переиспользуйте `event_key()` из `src/data.py` — тот же составной ключ, что
     и для дедупликации при скрапинге, чтобы не изобретать второй способ отличать
     одно событие от другого).

Ключи нужны, чтобы при поиске правильно сопоставить вектор конкретному событию,
даже если `events.json` с тех пор пополнился (тогда просто часть новых событий
не попадёт в поиск, пока вы не перезапустите `embed_events.py` — это нормально
и стоит явно сообщать пользователю в UI, а не тихо замалчивать).

Добавьте `data/event_embeddings.npy` в `.gitignore` (регенерируемый артефакт,
как и `*.joblib` из старого плана с классификатором).

## Шаг 5. src/search.py — семантический поиск

```python
def search_events(query: str, events: list[Event], top_n: int = 10) -> list[Event]:
    ...
```

Идея реализации:
1. Загрузить сохранённые эмбеддинги и ключи (шаг 4).
2. Отфильтровать: оставить только эмбеддинги тех событий, которые есть и в
   переданном `events` (уже отфильтрованном по датам/категориям/возрасту в
   `app.py`), и в сохранённых ключах — **поиск работает поверх остальных
   фильтров, а не вместо них**.
3. Посчитать эмбеддинг запроса той же моделью.
4. Косинусная близость (`sklearn.metrics.pairwise.cosine_similarity`) между
   вектором запроса и векторами кандидатов.
5. Вернуть `top_n` событий с наибольшей близостью.

**Проверка на актуальность:** cosine similarity — по-прежнему стандартная база
для поиска по эмбеддингам в 2026, не устарела. В продакшен-системах поверх неё
сейчас принято добавлять cross-encoder reranking (вторая модель, которая точнее
пересортировывает верхние результаты — cosine similarity находит "похожие по
теме", но не обязательно "точно отвечающие на запрос"). На 131 событии эта
разница пренебрежимо мала, а сложность/код удваиваются — осознанно ограничиваемся
cosine similarity без reranking.

**Кэширование модели** — важно для Streamlit: загрузка модели (даже маленькой)
занимает время, и её не нужно перезагружать при каждом перерисовывании страницы.
Оберните загрузку модели в `st.cache_resource` — попросите Claude Code объяснить
разницу между `st.cache_resource` и `st.cache_data`, прежде чем применять (одно
для тяжёлых объектов вроде моделей/клиентов, другое — для сериализуемых данных).

## Шаг 6. Поле поиска в сайдбаре

`st.sidebar.text_input("Поиск по смыслу", placeholder="например: что-то спокойное для трёхлетки")`
рядом с существующими фильтрами (даты/категории/возраст). Если поле не пустое —
применяете `search_events()` к уже отфильтрованному `filtered_events` и
используете результат вместо него для таблицы и карты; если пустое — оставляете
как было (никакого поиска, обычная фильтрация).

## Шаг 7. Проверка глазами

Попробуйте запросы, где нет дословного совпадения со словами в датасете, но есть
смысловая близость — например, "праздник на природе" (должно находить что-то
вроде уличного огненного шоу или экскурсии в парке, даже если этих слов нет в
названии) — и сравните с тем, что вернул бы обычный поиск по подстроке. Разница и
есть демонстрация того, зачем вообще нужны embeddings, а не TF-IDF.

## Как использовать Claude Code на этом этапе

- Спросите, почему `cosine_similarity`, а не, например, евклидово расстояние
  между векторами — для эмбеддингов направление вектора обычно важнее его длины,
  косинусная близость это учитывает, а евклидово расстояние — нет.
- Спросите объяснение `st.cache_resource` на конкретном примере вашего кода — что
  именно произойдёт (и с производительностью, и с ошибками), если использовать
  вместо него `st.cache_data` для модели.
- Если `pip install sentence-transformers` идёт болезненно долго/тяжело — это
  ожидаемо (PyTorch), не повод считать, что что-то сломалось.
